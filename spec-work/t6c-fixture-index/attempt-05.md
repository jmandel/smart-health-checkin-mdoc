# Appendix D. Fixture index and example-vector alignment

This appendix is informative. It indexes checked-in fixture material and explains how that material, future conformance vectors, and the worked examples in §16 align with the SMART Health Check-in 1.0 protocol. It does not define a new presentation flow, a new clinical request or response shape, production trust anchors, or additional conformance obligations.

The normative live presentation fixture class for version 1.0 is the same-device direct `org-iso-mdoc` flow defined in §8. In-person QR, NFC, deep-link, kiosk, pointer, relay, and completion-display material may be useful for demos or deployment diagnostics, but it is not SMART Health Check-in 1.0 protocol fixture material unless the captured phone page is itself running the §8 same-device flow and the indexed bytes are the §8 artifacts.

## D.1 Fixture classes and exactness levels

Fixture users need to know what kind of evidence each file provides before treating it as an oracle.

| Class | Use in this specification | Typical exactness |
| --- | --- | --- |
| Byte-exact fixture | A file whose bytes are intentionally compared exactly, such as a CBOR file, tag-24 boundary, digest input, hash, base64url string, or HPKE field. | Byte-exact for the named file or field only. |
| Structural fixture | A decoded JSON, CBOR diagnostic, or inspection report used to confirm fields, identifiers, wrappers, and relationships. | Structure-exact; map ordering, nondeterministic signatures, nonces, timestamps, and incidental debug fields may be outside scope. |
| Semantic example | A request or response object illustrating §5, §6, or §16 clinical semantics. | Semantic; JSON serialization is not byte-canonical unless a vector profile freezes it. |
| Diagnostic trace | A debug bundle, opened response inspection, or cross-library walk used for troubleshooting and regression analysis. | Diagnostic; useful for implementers but not a universal pass/fail oracle. |
| Historical archive | Real-platform or external material retained to document behavior at a point in time. | Historical; useful evidence, but not automatically current conformance after the spec changes. |
| Conformance-candidate vector | Stable fixture material that appears suitable for promotion once expected outcome, comparison mode, trust assumptions, and section coverage are frozen. | The future vector profile must say whether each check is byte-exact, structural, semantic, or diagnostic-only. |

Each fixture entry should identify the source, layer exercised, comparison mode, expected validator checks, privacy status, trust-material status, current classification, and follow-up needed before promotion.

## D.2 Privacy, security, and trust handling

Public fixtures and example vectors use synthetic data, demo keys, demo certificates, self-attested or test-only issuer material, and non-production trust anchors. Checked-in private keys are intentionally public fixture material only when the manifest says so, and they exist to reopen or validate named fixture bytes. They are not production key-management patterns.

Fixtures must not contain PHI, production private keys, bearer credentials, access tokens, reusable production launch URLs, or unredacted operational secrets. A capture or diagnostic bundle containing live PHI or production secrets is not a conformance artifact; it is sensitive production data that needs incident, audit, and retention handling. Fixture manifests should continue to record `containsPhi: false` or an equivalent statement, identify intentionally public test keys, and distinguish demo certificates from production trust material.

Diagnostic traces may include plaintext SMART requests, plaintext SMART responses, raw FHIR JSON, decrypted `DeviceResponse` bytes, `dcapiResponse` internals, or HPKE fields. Such traces are appropriate for controlled fixture review and regression tests, but routine telemetry and support bundles should redact or omit the same material unless explicitly authorized.

## D.3 Alignment with §16 worked examples

Section 16 supplies synthetic semantic examples for the clinical JSON model. Appendix D supplies fixture and vector organization for byte-oriented same-device material. The two should be aligned as follows:

- §16.1 insurance-card-only should map to a semantic request/response vector that uses `application/smart-health-card` with `value.verifiableCredential[]` and no Artifact-level `fhirVersion`.
- §16.2 US Core summary should map to a semantic raw-FHIR vector that preserves versioned `meta.profile` strings and treats `profiles[]` plus `profilesFrom[]` as additive selectors.
- §16.3 inline questionnaire should map to semantic vectors for the flattened selector shape, with `content.kind: "questionnaire"` and sibling `canonical` and/or `resource`; no nested `questionnaire` member appears in current v1.0 vectors.
- §16.4 mixed bundle should map to a semantic vector demonstrating one `application/fhir+json` Artifact fulfilling multiple items, with every fulfillment edge accepted by the corresponding item.
- §16.5 outcomes should map to semantic validation vectors for `partial`, `declined`, and `error`, including exact `requestStatus[]` coverage and safe `message` content.
- §16.6 no-selector share should map to a broad-selector semantic vector that remains clearly illustrative and does not imply a full-record export requirement.

The final public example-vector suite should contain JSON request/response files derived from §16, plus optional same-device wrapping vectors that carry one or more of those examples through §8. Until those files exist, §16 examples are semantic examples, not byte-exact fixtures.

## D.5 Expected file boundaries for same-device vectors

A complete same-device fixture set should make these boundaries explicit when the corresponding material is present:

1. SMART request JSON text and expected parsed `SmartHealthCheckinRequest`.
2. `ItemsRequest` CBOR bytes and tag-24 `ItemsRequest` bytes.
3. `DeviceRequest` CBOR bytes and unpadded base64url spelling used in the DC API request.
4. `encryptionInfo` CBOR bytes, unpadded base64url spelling, recipient public JWK/COSE_Key, and test-only private JWK when offline opening is intended.
5. `dcapiInfo`, SHA-256 handover, and `SessionTranscript` bytes, with the origin or origin-equivalent used for the vector.
6. Optional `readerAuth`, detached payload, reader public key or certificate evidence, and expected readerAuth classification.
7. SMART response JSON text and expected parsed `SmartHealthCheckinResponse`.
8. Tag-24 `IssuerSignedItem`, value-digest input, MSO, `issuerAuth`, and expected digest comparison.
9. `DeviceAuthentication` bytes, device public key evidence, device signature, and expected device-authentication result.
10. `DeviceResponse` plaintext, HPKE `enc`, HPKE ciphertext, `dcapiResponse` CBOR, and Digital Credentials API result JSON.
11. A validation report or expected inspection that records which checks are expected to pass, fail, be unsupported, or remain policy-dependent.

Byte-exact comparison should be limited to files or fields whose exact bytes the fixture profile names. Diagnostic notation, pretty-printed JSON, decoded inspection order, nondeterministic ECDSA signatures, nonce values, timestamps, localhost origins, package names, and demo certificate subjects should not become hidden requirements merely because they appear in a capture.

## D.6 Current gaps and promotion criteria

The current repository has useful same-device byte material, but several gaps remain before a public conformance-vector suite can be declared:

- **Clinical JSON refresh:** existing request captures and generated request fixtures include legacy nested `content.questionnaire` forms. Public v1.0 vectors need flattened Questionnaire selectors with sibling `canonical` and/or `resource` and no nested `questionnaire` member.
- **§16 semantic vector files:** the worked examples are canonical prose examples, but checked-in request/response JSON vector files derived from §16 still need to be generated or selected.
- **Conformance status labels:** manifests should distinguish byte-exact, structural, semantic, diagnostic, historical, implementation-regression, illustrative, and conformance-candidate use for each fixture root.
- **Expected validator reports:** promoted vectors need explicit expected results for §5 parsing, §6 response validation, §6.6 cross-validation, §8 wrapper validation, HPKE opening, mdoc digest/device checks, optional readerAuth, and Artifact-specific checks.
- **Determinism profile:** conformance vectors need a decision on deterministic CBOR map ordering, nonce/key handling, digestID conventions, deterministic or accepted-nondeterministic signatures, duplicate-map-key behavior, and exact base64url spelling.
- **Trust assumptions:** demo reader certificates, self-attested or test issuers, fixture private keys, local origins, and sample SHC issuers must remain labeled non-production unless a separate deployment profile explicitly accepts them.
- **Historical/demo separation:** external Mattr captures, kiosk/relay plans, SVG summaries, archived explainers, and deployment-local handoff artifacts should remain historical, illustrative, or demo-only unless a future extension defines a registered Artifact media type or future presentation profile.

A fixture should be promoted from diagnostic or historical status to conformance-vector status only after the fixture manifest states: the applicable profile label, target role, source section references, exact files and comparison modes, expected validation outcome, synthetic-data status, PHI status, trust-material status, and any policy-dependent checks that are intentionally out of scope.
