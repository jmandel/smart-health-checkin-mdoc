## Contradictions, missing pieces, and overreach

- **Transport boundary**: All attempts correctly kept the SMART response distinct from mdoc and kiosk envelopes. I retained that boundary from T1.C, which says the SMART response is the same clinical response object even when wrapped in mdoc, encrypted for kiosk submission, or processed locally (`spec-work/t1c-architecture-roles-flows/canonical.md` lines 30–35, 40–44).
- **Top-level and Artifact shape**: Attempts agreed on `type`, `version`, `requestId`, `artifacts[]`, `requestStatus[]`, Artifact `id`, `mediaType`, and `fulfills[]`. Active types and validators define the same response shape and status enum (`rp-web/src/sdk/core.ts` lines 47–83, 175–229), so the canonical makes those fields required and uses exact `"smart-health-checkin-response"` and `"1"` values.
- **Request binding**: Attempts agreed that `requestId` must equal the request `id`. T2.A requires Wallets/Responders to preserve request `id` for §6 response construction (`spec-work/t2a-clinical-request-model/canonical.md` lines 70–76), active docs list the same rule (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1082–1087), and active validation enforces it (`rp-web/src/sdk/core.ts` lines 254–267). The canonical uses exact string equality and rejects mismatches.
- **`requestStatus[]` exact coverage**: Attempts all required one status per request item, but active code currently checks unknown and missing statuses while duplicate detection occurs during response shape validation (`rp-web/src/sdk/core.ts` lines 211–228, 279–290). The active docs state that `requestStatus` includes one entry per original item (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1108–1120). I made exact, unique coverage normative, including an explicit note that zero-item requests remain dependent on §5.2.6 and schema closure.
- **Artifact `mediaType` vs. Artifact `type`**: Attempts aligned that Artifacts use `mediaType`, not a protocol type discriminator. T1.C's design principles say response forms are expressed as media types (`spec-work/t1c-architecture-roles-flows/canonical.md` lines 257–259), and active types use `mediaType` for all Artifact variants (`rp-web/src/sdk/core.ts` lines 53–75). The canonical prohibits a separate Artifact-level protocol discriminator.
- **Media type cross-checking**: Attempts made `mediaType ∈ accept[]` a Verifier rule, but active validator does not yet implement this cross-check; it only verifies `requestId`, `fulfills[]` references, and status coverage (`rp-web/src/sdk/core.ts` lines 254–292). T2.A already makes the request-side rule normative (`spec-work/t2a-clinical-request-model/canonical.md` lines 251–258, 525–545), and active docs list it as a response rule (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1088–1093). I kept the cross-check normative and recorded the implementation gap downstream.
- **SMART Health Card shape and FHIR version**: Attempts agreed that `application/smart-health-card` uses `value.verifiableCredential[]` and no outer `fhirVersion`. Active docs say SMART Health Cards carry authoritative FHIR version inside each signed credential (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 143–150, 1098–1100), and active tests reject SHC Artifacts with outer `fhirVersion` (`rp-web/src/protocol/index.test.ts` lines 134–159). I made Verifiers reject an outer `fhirVersion` and inspect signed payloads.
- **Raw FHIR JSON shape and FHIR version**: Attempts agreed that `application/fhir+json` requires outer `fhirVersion`; they differed on how strongly to state mixed-version Bundle handling. Active types require `fhirVersion` for raw FHIR (`rp-web/src/sdk/core.ts` lines 64–68, 243–246), and active docs require `fhirVersion` and say Bundle resources are interpreted under it (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1102–1106). The requested cutpoint explicitly asks for mixed-version Bundle prohibition, so the canonical makes Wallet mixing a SHALL NOT and Verifier detection a reject-or-quarantine rule.
- **`value`/`url`/`data` semantics**: Attempts varied between strict single-field use and flexible extension handling. Active code accepts `value`, `url`, or `data` for generic Artifacts without defining universal encoding or dereferencing (`rp-web/src/sdk/core.ts` lines 69–75, 248–250). The canonical requires `value` for the two core media types and requires extension definitions to supply any `url`, `data`, multi-field, integrity, and privacy semantics.
- **Status code semantics**: Attempts converged on `fulfilled`, `partial`, `unavailable`, `declined`, `unsupported`, and `error`. T2.A specifically leaves unsupported selectors, malformed known selectors found after initial parse, Questionnaire canonical/resource disagreement, unavailable content, declined items, partial fulfillment, and error for §6 (`spec-work/t2a-clinical-request-model/orchestrator-review.md` lines 27–33). The canonical maps unsupported selectors/media types/FHIR versions/Questionnaire ambiguity to `unsupported`; no content to `unavailable`; Holder refusal to `declined`; subset disclosure to `partial`; and operational failures after understanding to `error`.
- **Status-to-Artifact consistency**: Attempts 03 and 05 left room for extension or diagnostic combinations, while some wording in other attempts risked making every inconsistency a hard failure. I resolved this as SHOULD-level flagging: `fulfilled` and `partial` normally have Artifacts, while declined/unavailable/unsupported normally do not, but stricter disposition belongs to deployment profiles or extension definitions.
- **FHIR profile validation**: Attempts differed on whether Verifiers SHALL validate profile conformance. T2.A permits Wallet/Responder matching based on `meta.profile` or equivalent local knowledge rather than requiring full profile validation (`spec-work/t2a-clinical-request-model/canonical.md` lines 288–322). The canonical therefore makes `meta.profile` and `Bundle.entry[].resource.meta.profile` inspection SHOULD-level guidance and states that missing profile evidence is not automatically a core protocol error.
- **Overreach avoided**: I did not define mdoc response carriage, kiosk submission encryption, EHR write-back, clinical reconciliation, issuer trust rules, universal Artifact size limits, universal `url` dereferencing, universal `data` encoding, or final registry procedures. Those belong to §8, §9, downstream workflow policy, Appendix B, Appendix H, or §13.

## Resolutions with repository evidence

- Preserved the transport-neutral response object framing from accepted T1/T2 canonicals: SMART responses are part of the clinical content model and remain distinct from transport wrappers (`spec-work/t1a-editorial-terminology/canonical.md` lines 180–188; `spec-work/t1c-architecture-roles-flows/canonical.md` lines 30–35).
- Used the active response field and Artifact shapes from TypeScript: `SmartCheckinResponse` has `type`, `version`, `requestId`, `artifacts`, and `requestStatus`; Artifact variants use `mediaType`, `fulfills`, SHC `value.verifiableCredential`, raw FHIR `fhirVersion`, and generic `value`/`url`/`data` (`rp-web/src/sdk/core.ts` lines 47–83).
- Grounded validation strictness in active code: response validators enforce fixed response `type`/`version`, non-empty `requestId`, arrays for `artifacts` and `requestStatus`, Artifact id uniqueness, non-empty `fulfills[]`, SHC no outer `fhirVersion`, raw FHIR `fhirVersion`, status enum, and status-message strings (`rp-web/src/sdk/core.ts` lines 175–252).
- Grounded cross-request validation in active code and tests: `validateResponseAgainstRequest` rejects requestId mismatches, unknown `fulfills[]`, unknown status items, and missing status items (`rp-web/src/sdk/core.ts` lines 254–292); tests exercise SHC response validation, outer `fhirVersion` rejection, and response references against request items (`rp-web/src/protocol/index.test.ts` lines 134–190).
- Preserved active documentation's response rules: docs require `requestId` equality, Artifact id uniqueness, `fulfills[]` item ids, `mediaType` in each fulfilled item's `accept[]`, many-to-many fulfillment, SHC `verifiableCredential[]` with no outer `fhirVersion`, raw FHIR `fhirVersion`, Bundle interpretation under that `fhirVersion`, no profile summary field, and per-item status codes (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1080–1120).
- Preserved active examples: documentation and protocol explainer show response JSON with `type`, `version`, `requestId`, raw FHIR Artifact `fhirVersion`, `fulfills[]`, and `requestStatus[]` (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 941–1048; `docs/PROTOCOL-EXPLAINER.md` lines 219–273).
- Preserved T2.A request-side dependencies: item ids are exact scoped strings, `accept[]` is per-item and ordered, Wallets/Responders must not return unaccepted media types, and `fhirVersions[]` applies to raw FHIR JSON but not SMART Health Cards (`spec-work/t2a-clinical-request-model/canonical.md` lines 219–258, 525–545).

## Downstream decisions

- Appendix B should encode required response fields, fixed response `type` and `version`, Artifact id uniqueness where possible, non-empty `fulfills[]`, response status enum, `requestStatus[].item` uniqueness where possible, SHC no outer `fhirVersion`, raw FHIR required `fhirVersion`, and generic Artifact body-field requirements.
- Appendix B or conformance tooling will need procedural validation for constraints JSON Schema cannot fully express, especially `requestStatus[]` covering every original request item exactly once and Artifact `mediaType` being accepted by each fulfilled item's `accept[]`.
- Appendix H should align FHIR Bundle handling, single-resource handling, `meta.profile`, profile-family membership, `QuestionnaireResponse.questionnaire`, `|version` comparisons, and mixed-FHIR-version guidance with §§5–6.
- §13 should define status-code registry procedures, extension media-type registration, selector-kind registration, and compatibility rules for `accept[]` substitution.
- §8 and §9 should carry this SMART response without redefining clinical semantics and should invoke §6.6 validation after extracting or decrypting the SMART response.
- §11 and §12 should revisit status `message` privacy, extension `url` dereferencing, `data` encoding, raw FHIR provenance limits, response retention, and logging/telemetry handling.
