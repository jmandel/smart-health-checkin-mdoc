## Strongest contributions

- **Attempt 01**: Best concise end-to-end appendix structure and strong separation of schema validation from §6.6 procedural checks. It also correctly preserved `profilesFrom[]` as a non-empty canonical URL array and avoided making `items[]` non-empty.
- **Attempt 02**: Best schema-use conventions and examples, including clear notes on requester identity metadata limits, additive selectors, generic Artifact `value`/`url`/`data`, and media-type-specific response branches.
- **Attempt 03**: Strongest procedural-validation table with explicit source-rule framing, good treatment of duplicate JSON member names, and useful FHIR/SMART Health Card validation boundaries.
- **Attempt 04**: Best compact common definitions, best id-string caution, and clearest examples of generic extension Artifacts without inventing extension semantics.
- **Attempt 05**: Best emphasis that `profiles[]` and `profilesFrom[]` must remain additive, that extension branches should stay permissive, and that Appendix B should not define mdoc, kiosk, registry, or full FHIR behavior.

## Contradictions, missing pieces, and overreach

- **Schema dialect**: Attempts used JSON Schema 2020-12 consistently, though some phrased support as SHOULD. I made Appendix B schema-conformance use 2020-12 semantics because the snippets use `$defs`, `const`, `oneOf`, `anyOf`, and `not`.
- **Top-level request shape**: Attempts agreed on fixed request `type`/`version`, required `id`, and optional `purpose`/`fhirVersions`. Accepted §5 requires `type`, `version`, `id`, and `items` and permits `purpose` and `fhirVersions` (`spec-work/t2a-clinical-request-model/canonical.md` lines 43-59). Active TypeScript validates the same fields (`rp-web/src/sdk/core.ts` lines 87-104).
- **`items[]` non-empty**: Some attempts added or considered `minItems: 1`; others preserved the accepted SHOULD. I did not set `items.minItems` because accepted §5.2.6 says Requesters SHOULD include at least one item and explicitly notes active validators accept an empty array (`spec-work/t2a-clinical-request-model/canonical.md` lines 94-99). Active TypeScript only checks that `items` is an array (`rp-web/src/sdk/core.ts` line 103).
- **Item-id and Artifact-id uniqueness**: Attempts varied on whether JSON Schema can enforce uniqueness. I left uniqueness to procedural validation because portable JSON Schema cannot enforce uniqueness by `items[].id`, `artifacts[].id`, or `requestStatus[].item`; accepted §§5-6 make those semantic constraints explicit (`spec-work/t2a-clinical-request-model/canonical.md` lines 219-225; `spec-work/t2b-clinical-response-model/canonical.md` lines 66-70 and 269-274). Active validators enforce these procedurally (`rp-web/src/sdk/core.ts` lines 104-114, 189-221).
- **`profilesFrom[]` shape**: All attempts preserved array shape, but their URL patterns differed. I used a conservative HTTP(S) URL-string pattern and recorded that it is not a full FHIR canonical validator. Accepted §5 requires `profilesFrom` as a non-empty array and rejects string/object/package/URN forms unless a future version or extension defines them (`spec-work/t2a-clinical-request-model/canonical.md` lines 296-305). Active tests reject string and object `profilesFrom` values (`rp-web/src/protocol/index.test.ts` lines 82-110).
- **`profiles[]` and `resourceTypes[]` array sizes**: Some attempts omitted `minItems` for present arrays. Accepted §5 says `profiles[]` and `resourceTypes[]` are arrays of one or more strings when included (`spec-work/t2a-clinical-request-model/canonical.md` lines 288-292 and 306-310), so the canonical schema uses `minItems: 1` for these present arrays while preserving the no-selector default when all selector arrays are omitted.
- **Additive profile selectors**: Attempts agreed that `profiles[]` and `profilesFrom[]` must both be allowed. I retained permissiveness and did not encode a narrowing relationship, matching accepted §5.4.1.4 (`spec-work/t2a-clinical-request-model/canonical.md` lines 316-322), Appendix H (`spec-work/t2c-fhir-mapping-appendix/canonical.md` lines 60-65), active docs (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1070-1074), and active fixture vectors (`wallet-android/app/src/test/resources/test-vectors.json` lines 30-30).
- **Questionnaire forms**: Attempts agreed on canonical string, inline `Questionnaire`, and object forms with `canonical`, `resource`, or both. I used `anyOf` for the reference union to avoid accidental `oneOf` failures if a future valid Questionnaire resource happens to overlap an object-reference shape. Accepted §5 defines these forms and requires inline resources to have `resourceType: "Questionnaire"` (`spec-work/t2a-clinical-request-model/canonical.md` lines 369-427).
- **Extension selectors**: Attempts varied between closed core schemas and permissive extension branches. I kept a non-core `kind` extension branch so Appendix B does not block registered extension selectors. Accepted §5 treats unknown `content.kind` as an extension selector that must not be guessed (`spec-work/t2a-clinical-request-model/canonical.md` lines 486-499). Active TypeScript currently rejects unknown selector kinds (`rp-web/src/sdk/core.ts` lines 137-169), so extension support remains a downstream implementation/registry issue rather than a reason to close the base appendix schema.
- **Requester identity metadata**: Attempts correctly noted that schema cannot fully enforce §5.2.7 without closing extensions. I preserved the prohibition as a procedural check because accepted §5 forbids identity metadata across top-level, item, selector, and extension members (`spec-work/t2a-clinical-request-model/canonical.md` lines 100-112), while the schema keeps unknown members open.
- **Top-level response and Artifact shape**: Attempts agreed on fixed response `type`/`version`, `requestId`, `artifacts[]`, `requestStatus[]`, common Artifact `id`/`mediaType`/`fulfills[]`, and status enum. Accepted §6 and active types define the same response model (`spec-work/t2b-clinical-response-model/canonical.md` lines 7-49; `rp-web/src/sdk/core.ts` lines 47-83).
- **SMART Health Card branch**: Attempts agreed that `application/smart-health-card` requires `value.verifiableCredential[]` and no outer `fhirVersion`. Accepted §6 requires that shape and requires Verifiers to reject an outer `fhirVersion` (`spec-work/t2b-clinical-response-model/canonical.md` lines 111-122 and 372-379). Active tests exercise the rejection (`rp-web/src/protocol/index.test.ts` lines 134-159).
- **Raw FHIR JSON branch**: Attempts agreed that `application/fhir+json` requires `fhirVersion` and `value`; they differed on how deeply to validate FHIR. I required a JSON object `value` with `resourceType` and left Bundle traversal and full FHIR validation procedural, matching §6 and Appendix H (`spec-work/t2b-clinical-response-model/canonical.md` lines 138-155; `spec-work/t2c-fhir-mapping-appendix/canonical.md` lines 87-121).
- **Generic/extension Artifacts**: Attempts varied on whether to allow `fhirVersion` or multiple body fields. I required non-core `mediaType` and at least one of `value`, `url`, or `data`, while leaving additional members open and stating that extension media types define combined-field and FHIR-version semantics. This matches accepted §6.3.3 (`spec-work/t2b-clinical-response-model/canonical.md` lines 185-196) and active validation (`rp-web/src/sdk/core.ts` lines 248-250).
- **Cross-document validation**: Attempts sometimes used normative schema language for `requestId`, `fulfills[]`, media-type acceptance, and `requestStatus[]` coverage. I moved those to B.4 because JSON Schema cannot validate a standalone response against the original request. Accepted §6.6 requires those Verifier checks (`spec-work/t2b-clinical-response-model/canonical.md` lines 348-379), and active code implements a subset (`rp-web/src/sdk/core.ts` lines 254-292).
- **Overreach avoided**: I did not define mdoc or kiosk behavior, a profile-family registry, FHIR package resolution, universal URL dereferencing, full FHIR profile validation, SMART Health Card signature validation, hard byte/string limits, or separate checked-in schema files. Those belong to later sections, registries, deployment profiles, or tooling.

## Resolutions with repository evidence

- Preserved the transport-neutral clinical boundary from accepted T1/T2: SMART requests and responses retain their clinical meaning across presentation transports, while mdoc and kiosk wrappers are separate payload domains (`spec-work/t1b-purpose-scope-goals/canonical.md` lines 7-18; `spec-work/t1c-architecture-roles-flows/canonical.md` lines 22-35).
- Grounded request field shape and validation in accepted §5 and active TypeScript: fixed request `type` and `version`, non-empty `id`, optional string `purpose`, optional array-of-strings `fhirVersions`, array `items`, required item `id`/`title`/`content`/`accept`, non-empty `accept[]`, and selector validation (`spec-work/t2a-clinical-request-model/canonical.md` lines 43-99 and 200-261; `rp-web/src/sdk/core.ts` lines 87-173).
- Grounded `profilesFrom[]` and additivity in accepted §5, Appendix H, docs, tests, and fixtures: non-empty canonical URL array, no string/object/package/URN shapes, and additive `profiles[]` plus `profilesFrom[]` (`spec-work/t2a-clinical-request-model/canonical.md` lines 296-322; `spec-work/t2c-fhir-mapping-appendix/canonical.md` lines 52-65; `rp-web/src/protocol/index.test.ts` lines 82-110; `wallet-android/app/src/test/resources/test-vectors.json` lines 30-30).
- Grounded response field shape and status enum in accepted §6 and active TypeScript: response `type`, `version`, `requestId`, `artifacts`, `requestStatus`, status codes, Artifact common fields, core media types, and generic body fields (`spec-work/t2b-clinical-response-model/canonical.md` lines 7-49 and 51-108; `rp-web/src/sdk/core.ts` lines 47-83 and 175-252).
- Grounded SHC and raw FHIR branch rules in accepted §6, active docs, and tests: SMART Health Cards use `value.verifiableCredential[]` and no outer `fhirVersion`; raw FHIR JSON uses `fhirVersion` and `value` (`docs/SMART-HEALTH-CHECKIN-REQUEST-RESPONSE.md` lines 1098-1104; `rp-web/src/protocol/index.test.ts` lines 113-159; `rp-web/src/sdk/core.ts` lines 232-247).
- Grounded procedural validation in accepted §6.6 and active code: `requestId` matching, fulfillment-reference resolution, `requestStatus[]` coverage, raw FHIR version checks, Bundle/profile guidance, and media-type acceptance are Verifier cross-checks, not standalone response-schema checks (`spec-work/t2b-clinical-response-model/canonical.md` lines 348-388; `rp-web/src/sdk/core.ts` lines 254-292).
- Grounded FHIR limitations in accepted Appendix H: profile-family membership needs implementation-guide/package/family-map/local knowledge, Bundle traversal inspects `Bundle.entry[].resource`, SMART Health Cards require signed-payload inspection, and full FHIR profile validation is outside core protocol validation (`spec-work/t2c-fhir-mapping-appendix/canonical.md` lines 52-58, 87-127, and 196-206).

## Downstream decisions

- Appendix A should index schema-conformance requirements only where Appendix B deliberately states them or restates §§5-6; procedural §§5-6 validation requirements should remain separately indexed.
- Conformance tooling should pair these schemas with procedural validators for duplicate ids/status items, duplicate JSON object member detection where possible, `requestId`, `fulfills[]`, `requestStatus[]` coverage, per-item `accept[]`, FHIR version consistency, Bundle traversal, profile-family membership, QuestionnaireResponse comparison, and SMART Health Card validation.
- §13 registry work should define how extension selector schemas, extension Artifact media-type schemas, media-type compatibility rules, and any future status-code extensions compose with the base schemas.
- Future publication may extract these snippets into separate `.schema.json` artifacts, but this cutpoint intentionally writes Markdown appendix snippets only.

## Open issues

- No blocking open issues for T2.D canonical text.
- Final conformance closure may still choose stricter id patterns, maximum lengths, maximum array sizes, transport byte limits, or `items[]` `minItems: 1`; those changes require corresponding normative body text rather than silent schema tightening.
- Extension schema composition, extension-media-type FHIR-version semantics, and status-code extension handling remain dependent on §13 and deployment profiles.
- The HTTP(S) pattern used for `profilesFrom[]` is intentionally lightweight. If final §5 or registry work broadens or narrows canonical URL syntax, Appendix B should be revised deliberately.
