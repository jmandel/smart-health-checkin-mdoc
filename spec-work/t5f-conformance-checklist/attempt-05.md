# Appendix A. Conformance checklist

This appendix is an inventory of testable requirements defined in the normative sections of SMART Health Check-in 1.0. It does not create independent obligations. Optional-profile rows apply only to implementations that claim the referenced feature or to deployment profiles that make the feature mandatory.

| ID | Target | Level | Section | Checklist item | Evidence/validation |
| --- | --- | --- | --- | --- | --- |
| A-001 | Requester/Verifier | SHALL | §4.1.1 | Identify each claimed conformance target, feature/profile, specification version, and deployment profile. | Conformance statement lists target(s), profile labels, version, and policy dependencies. |
| A-002 | Holder Wallet/Responder | SHALL | §4.1.2 | Validate SMART requests under §5 before response construction and preserve request item ids. | Negative request tests fail safely; valid ids appear unchanged in `fulfills[]` and `requestStatus[].item`. |
| A-003 | Phone presenter | SHALL | §4.1.3 | For kiosk support, parse pointer-only URLs, bind wrapper identifiers, open and verify the wrapper, validate `smartRequest`, and re-enter §8. | Kiosk trace shows pointer/envelope/JWS/payload binding and fresh phone-local §8 request construction. |
| A-004 | Kiosk creator | SHALL | §4.1.4 | Embed the clinical request directly as `KioskRequestPayload.smartRequest` and not as `requestProfile`, preset, IPS shortcut, profile label, or helper wrapper. | Signed payload contains `smartRequest`; negative fixtures with alternate wrappers are rejected or never emitted. |
| A-005 | Completion display | SHALL | §4.1.5 | Before workflow use, decrypt candidate submissions, bind wrapper `requestId`, validate SMART response under §6, apply §6.6 against original `smartRequest`, and account for §8 validation. | Completion logs/test vectors show all validation steps before accepted workflow state. |

## Organizer notes

### Strengths

- The table is intentionally granular: most rows map one conformance target to one stable section and one testable requirement.
- It covers the base §5/§6 SMART model, §7 trust separation, §8 `org-iso-mdoc`, optional `readerAuth`, §9 kiosk wrapper and provider behavior, §§11-14 cross-cutting obligations, and §13 registries.
- Stale `requestProfile`, preset, IPS, “all of the above”, dynamic-element, and inline-§8 kiosk-fragment patterns appear only as negative checks.

### Caveats

- Some rows cluster closely related validation checks where the canonical section itself defines a checklist or multi-field envelope shape; fixture authors may split these further.
- Requirement levels follow the referenced canonical text; rows marked SHOULD or MAY should not be promoted to mandatory certification gates unless a deployment or test profile says so.
- This draft uses §4.1 target labels plus compatible role labels where the canonical section narrows a role, but the organizer may prefer stricter normalization of target names.

### Open issues

- Appendix B/C/D/H final text may add schema, CDDL, fixture, and FHIR-mapping row ids that should be cross-linked or substituted for some evidence descriptions.
- Zero-item requests remain a §5.2.6 SHOULD-level concern pending Appendix B/conformance closure.
- Some active implementation notes in §9 mention prototype limits and provider shapes; profile authors should decide which become fixture requirements versus implementation evidence.

### Downstream dependencies

- T6 examples and fixture index should reference these row ids or the organizer's final row ids.
- External conformance tests should include negative vectors for stale wrappers, wrong wire identifiers, algorithm downgrades, id substitution, raw-FHIR provenance overclaims, and plaintext relay leakage.
