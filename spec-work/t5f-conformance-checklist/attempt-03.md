# Appendix A. Conformance checklist

This appendix is an inventory of testable obligations defined elsewhere in SMART Health Check-in 1.0. It does not create independent requirements. Each row identifies one conformance target, one source section, a requirement level, and an evidence expectation for certification, test, or implementation review.

| ID | Target | Level | Section | Checklist item | Evidence/validation |
| --- | --- | --- | --- | --- | --- |
| A-001 | Requester/Verifier | SHALL | §4.1 | State the implemented target, feature/profile label, specification version, and any deployment profile for each conformance claim. | Conformance statement enumerates target(s), feature(s), version `1`, profile labels, and deployment-policy dependencies. |
| A-002 | Requester/Verifier | SHALL | §5.1 | Encode SMART requests as RFC 8259 JSON UTF-8 without comments, duplicate member names, non-JSON numeric values, or non-object top level. | Parser and negative tests reject malformed JSON, duplicate keys where detected, non-object top level, comments, trailing commas, `NaN`, and infinities. |
| A-003 | Requester/Verifier | SHALL | §5.2 | Construct `SmartHealthCheckinRequest` with exact `type`, exact `version`, non-empty `id`, and `items[]`. | Request fixtures validate `type: "smart-health-checkin-request"`, `version: "1"`, non-empty request id, and array `items`. |

## Organizer notes

### Strengths

- Covers the accepted target set from §4.1, including Requester/Verifier, Holder Wallet/Responder, Phone presenter, Kiosk creator, Completion display, Submission service/provider, deployment/profile authors, and conformance/fixture authors.
- Keeps rows as an index into existing sections rather than creating new standalone requirements.
- Explicitly includes negative checks for stale `requestProfile`, preset, IPS shortcut, “all of the above”, and legacy inline §8 kiosk-fragment patterns.
- Separates clinical request/response validation, trust-layer interpretation, same-device mdoc mechanics, kiosk wrapper mechanics, registries, security, privacy, and internationalization.

### Caveats

- Some rows intentionally cluster tightly coupled validation steps where the canonical section itself defines a checklist, especially §§8.7-8.8 and §§9.7-9.9.
- The checklist uses provisional profile labels from §§4 and 13; final publication may replace them with registry URIs or a formal identifier syntax.
- Appendix B/C/D fixture rows should be reconciled after final schema, CDDL, byte-ladder, and fixture-index text is locked.

### Open issues

- Zero-item request handling remains a SHOULD/non-hard requirement in §5.2.6 and Appendix B; certification profiles may decide whether to prohibit it.
- Some active kiosk implementation details are stricter on id, algorithm, content type, and expiration than on every mirrored non-id metadata value; conformance vectors should decide how strict to be.
- The active successful kiosk submission currently carries `smartResponse`; any future validation-evidence payload kind needs registry/profile review without weakening §8 validation.

### Downstream dependencies

- T6 examples and fixture index should map each fixture/vector to one or more Appendix A row ids.
- Final registry publication should replace provisional labels only if the same target/feature meanings are preserved.
- Any future OID4VP binding must add its own checklist rows rather than claiming satisfaction of §8 or §9 rows by implication.
