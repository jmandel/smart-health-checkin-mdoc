# T5.F adjudication — Appendix A conformance checklist

## Inputs reviewed

I reviewed `spec.md.outline`, `spec.md.outline.dependency_tree`, `spec-work/methodology.md`, all five T5.F attempts, accepted canonical material for T1-T5.E, and active implementation/docs/fixtures where checklist claims were contested. Decisive sources were the accepted conformance target taxonomy in `spec-work/t5a-conformance/canonical.md`, clinical request/response rules in T2.A/T2.B, trust and same-device/kiosk rules in T3/T4, cross-cutting T5.B-T5.E, and active code/docs confirming current identifiers and stale-flow removals.

## Attempt comparison

- All attempts correctly framed Appendix A as an index of existing obligations, not a new source of normative behavior. I retained that framing because §4.7 says Appendix A SHALL link to stable source sections and SHALL NOT create independent obligations.
- Attempts 03-05 were strongest on §4.1 target coverage. Attempts 01-02 underweighted Phone presenter, Completion display, Submission service/provider, Deployment/profile author, and Conformance/fixture author rows, which are explicit targets in §4.1.3-§4.1.7.
- Attempts 03 and 05 had the best request/response coverage, especially `profilesFrom[]`, additive `profiles[]`/`profilesFrom[]`, questionnaire forms, `fhirVersions[]`, many-to-many fulfillment, and §6.6 cross-validation. I adopted those claims but split rows where a draft combined multiple targets or multiple section anchors.
- Attempts 02, 03, and 05 captured the optional nature of `readerAuth`; attempt 01 sometimes implied it more broadly. I treated `readerAuth` rows as Optional-profile or Conditional, consistent with §4.3.3, §7.2, §8.2.4, and Appendix C.4.
- Attempts 04 and 05 were strongest on stale-flow guardrails. I retained negative rows for rejected behaviors only where the accepted spec has an explicit source, such as direct `smartRequest` embedding (§4.1.4, §9.1, §9.4), pointer-only QR (§9.6), no `readerAuthAll` (§8.2.4 / C.4), no profile labels as request shortcuts (§13.5), and no locale negotiation fields (§14.1).

## Decisive evidence and accepted claims

- **Targets and profile labels:** §4.1 defines Requester / Verifier, Holder Wallet / Responder, Phone presenter, Kiosk creator, Completion display, Submission service/provider, Deployment/profile author, and Conformance/fixture author. §4.4 and §13.5 define provisional labels including `smart-health-checkin-core-1`, `smart-health-checkin-mdoc-dcapi-1`, `smart-health-checkin-kiosk-1`, `smart-health-checkin-readerauth-1`, and `smart-health-checkin-fixtures-1`.
- **Clinical request:** §5 requires RFC 8259 / UTF-8 request JSON, fixed `type` and `version`, session-scoped request `id`, request items with unique ids, Holder-facing display fields, advisory `required`, selector validation, `profilesFrom[]` as non-empty canonical array, additive profile semantics, questionnaire forms, canonical `|version` handling, and per-item ordered `accept[]`.
- **Clinical response:** §6 requires fixed response shape, exact `requestId`, Artifact ids/media types/content/`fulfills[]`, SMART Health Card and raw FHIR JSON rules, complete `requestStatus[]`, status-code semantics, privacy-safe messages, many-to-many validation, and §6.6 cross-validation against the original request.
- **Trust/provenance:** §7 and §11 separate origin, reader, issuer/device, clinical-source, kiosk wrapper, encryption, and deployment policy. §7.4.2 and §11.5 make raw `application/fhir+json` patient-mediated unless separately provenanced/signed; SMART Health Card JWSs still require SHC verification and policy evaluation.
- **Same-device:** Appendix C and §13.2 confirm `org-iso-mdoc`, `org.smarthealthit.checkin.1`, namespace `org.smarthealthit.checkin`, element `smart_health_checkin_response`, request key `org.smarthealthit.checkin.request`, DeviceRequest version `1.0`, tag-24 `ItemsRequest`, exact `SessionTranscript`, HPKE DHKEM(P-256, HKDF-SHA256)/HKDF-SHA256/AES-128-GCM, empty AAD, and stable response extraction. Active code exports the same constants in `rp-web/src/protocol/index.ts` and docs confirm them in `docs/profiles/org-iso-mdoc.md`.
- **Reader authentication:** §7.2, §8.2.4, Appendix C.4, and docs/code confirm optional per-`DocRequest.readerAuth`, not v1.1 `readerAuthAll`; when present it is detached `COSE_Sign1` with payload `null`, empty external AAD, protected alg `-7`, exact `ReaderAuthentication` detached payload, and COSE header label 33 `x5chain`.
- **Kiosk:** §9.1-§9.12 and Appendix C.K require direct `smartRequest`, compact kiosk request JWS, encrypted request envelope, pointer-only `#r`, phone validation/re-entry into fresh §8, active `SubmissionPlaintext.payload.kind`, response-submission encryption, untrusted provider constraints, completion validation, replay/freshness controls, and metadata minimization. Active tests in `rp-web/src/kiosk/kiosk-provider.test.ts` assert pointer-only URLs, direct `smartRequest`, no stale request/preset fields, active payload kind, and no raw `dcapiResponse`/`deviceResponse` in submission payloads.
- **Registry, security, privacy, i18n:** §11-§14 add exact cryptographic separation, replay/freshness, relay opacity, minimization, telemetry, provisional registry status, designated expert review, exact-value identifier comparison, no protocol locale negotiation, and safe Unicode/BIDI handling.
- **Fixture authoring:** §4.1.7, §4.3.5, Appendix D, Appendix D.K, and `fixtures/README.md` require metadata about target, feature, section, expected outcome, comparison mode, trust status, PHI/test-key status, and classification. T4.D explicitly notes no checked-in deterministic `fixtures/kiosk/` suite at this cutpoint, so I did not claim one exists.

## Rejected or narrowed claims

- I rejected any positive checklist item for `requestProfile`, preset/presetId, IPS shortcut, “all of the above,” profile label negotiation, or SDK helper wrappers as kiosk clinical request carriers. Accepted text requires direct `smartRequest` and §13.5 rejects profile identifiers as in-band request fields.
- I rejected inline §8 QR fragments, `deviceRequest`/`encryptionInfo` in QR, `shc1j`/`shc1d` fallback encodings, dynamic mdoc claim names, and `readerAuthAll` as positive v1.0 requirements. Current accepted sections require pointer-only QR and direct `org-iso-mdoc` v1.0 per-`DocRequest.readerAuth` when reader auth is used.
- I rejected rows that treated successful HPKE opening, mdoc issuer/device validation, kiosk wrapper validation, provider row presence, `requestId` equality, or Holder action as clinical-source provenance, patient identity, consent, or downstream authorization. The trust sections explicitly prohibit substituting trust layers.
- I did not promote active implementation numeric limits such as 25 MiB kiosk plaintext or 32-byte nonces into universal base rows. They appear only as deployment/profile or fixture evidence where the accepted canonical text keeps them non-universal.
- I avoided claiming current deterministic kiosk vectors exist. Appendix D.K says no checked-in deterministic `fixtures/kiosk/` suite was verified; the checklist instead includes optional fixture-profile author obligations and future-vector expectations.

## Risks, gaps, and handling choices

- Some source sections are still appendix-oriented or pseudo-CDDL-oriented. Where exact byte behavior is accepted in Appendix C/C.K, I used those stable appendix anchors rather than inventing new §8/§9 details.
- Several obligations naturally involve more than one actor. Because the user required exactly one target per row, I split construction and validation responsibilities into separate rows where needed.
- Some rows are optional-feature scoped. I marked same-device, kiosk, readerAuth, fixture, extension, and deployment-profile rows as `Optional-profile`, `Conditional`, `SHOULD`, or target-specific rather than implying every conforming implementation must implement every optional flow.
- Security, privacy, registry, and internationalization rows were kept as checklist cross-links to concrete obligations, not broad restatements. The canonical checklist remains terse and testable.
