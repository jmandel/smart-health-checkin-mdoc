## Appendix A. Conformance checklist

This appendix is an inventory of conformance obligations defined elsewhere in SMART Health Check-in 1.0. It does not create independent requirements. Optional-feature rows apply only to implementations that claim the feature or to deployment profiles that make the feature mandatory.

| ID | Target | Level | Section | Checklist item | Evidence/validation |
| --- | --- | --- | --- | --- | --- |
| A-001 | Requester / Verifier | SHALL | §4.1.1 | A conformance claim identifies target, feature/profile, specification version, and applicable deployment profile. | Test report or declaration names target(s), profile label(s), version, and deployment policy. |
| A-002 | Requester / Verifier | SHALL | §5.1 | Encode each SMART request as RFC 8259 JSON and UTF-8 when serialized. | Parser rejects non-object, malformed JSON, duplicate names when detected, comments, trailing commas, and non-JSON values. |
| A-003 | Requester / Verifier | SHALL | §5.2 | Construct a `SmartHealthCheckinRequest` with required `type`, `version`, `id`, and `items`. | JSON validation shows exact `type: "smart-health-checkin-request"`, exact `version: "1"`, non-empty request `id`, and array `items`. |
| A-004 | Holder Wallet / Responder | SHALL | §5.2 | Reject SMART requests with absent or incompatible `type` or `version`. | Negative tests for missing/wrong discriminator and version fail before response construction. |
| A-005 | Requester / Verifier | SHALL NOT | §5.2.7 | Do not place requester identity, origin, reader, trust, kiosk, callback, logo, endpoint, certificate, or wrapper metadata in the SMART request body. | Request examples and generated payloads contain clinical request fields only; negative fixture with requester-identity metadata is rejected or treated as non-trust data. |
| A-006 | Holder Wallet / Responder | SHALL NOT | §5.2.7 | Do not treat SMART request body fields as authenticated requester identity. | UI/trust review distinguishes `purpose`, titles, summaries, selectors, and unknown members from authenticated origin/reader/creator signals. |

### Organizer notes

**Strengths**

- Covers the major normative surfaces from §§4-14 while keeping Appendix A an index rather than a source of new rules.
- Uses one target, one level, and one stable section reference per row.
- Includes negative checks for stale `requestProfile`, preset, IPS shortcut, profile-label, dynamic mdoc element, and inline §8 kiosk-fragment patterns.
- Separates base clinical request/response obligations from optional mdoc, `readerAuth`, kiosk, registry, fixture, security, privacy, and i18n obligations.

**Caveats**

- Some rows cluster closely related checks from a single section to keep the checklist usable; organizers may split them further for certification test planning.
- `SHALL NOT` rows are represented with `SHALL NOT` as the level because the source obligations are explicit prohibitions.
- The exact final Appendix B/C/D/H row set may need adjustment after schema, CDDL, and fixture appendices are finalized.

**Open issues**

- Decide whether zero-item SMART requests become a hard schema failure; §5.2.6 currently leaves non-empty `items[]` as SHOULD.
- Decide which fixture roots are conformance vectors versus diagnostics, historical captures, or implementation regression material.
- Decide how §8 validation evidence is represented across the active kiosk submission path when the submitted payload contains only the SMART response wrapper.

**Downstream dependencies**

- Appendix B should align schema-test rows with A-002 through A-046.
- Appendix C/D/E should align byte-level and fixture rows with A-053 through A-071 and A-125 through A-128.
- Registry publication should align provisional profile labels and exact wire identifiers with A-111 through A-117.
