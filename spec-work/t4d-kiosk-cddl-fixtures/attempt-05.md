# Appendix C kiosk pseudo-CDDL / schema material

This material extends Appendix C with profile-constrained JSON shapes for the cross-device kiosk wrapper defined in §9. It is intended for implementers, fixture authors, and conformance-tool authors who need stable field names, byte inputs, and row boundaries for kiosk request publication and response submission.

These snippets are pseudo-CDDL / JSON shape guidance. They are not complete JOSE, JWK, JSON Schema, InstantDB, WebCrypto, or ISO/IEC 18013-5 CDDL. They restate the version 1.0 kiosk profile constraints from §§9.1-9.12. If this appendix conflicts with normative §9 prose, §9 controls.

The kiosk request-envelope crypto, the kiosk response-submission crypto, and the §8 same-device HPKE response crypto are distinct constructions. The kiosk wrapper never carries inline §8 `deviceRequest`, §8 `encryptionInfo`, §8 `SessionTranscript`, §8 `dcapiResponse`, or §8 HPKE ciphertext in the Pointer URL or provider request row.

## C.K.1 Notation and constants

`JSONString(X)` denotes UTF-8 JSON text whose parsed value has shape `X`. `b64u` denotes base64url without padding. `NumericDateMs` denotes a finite JSON number containing milliseconds since the Unix epoch. `P256JWK` denotes a public JWK usable for the stated P-256 ECDH or ES256 operation; this appendix does not define full JWK validation.

Version 1.0 kiosk constants are:

```text
kiosk-request-jws-typ        = "smart-health-checkin+kiosk-request+jws"
kiosk-request-content-type   = "application/smart-health-checkin-kiosk-request+jws+aesgcm"
kiosk-wrapper-suite          = "ECDH-P256+HKDF-SHA256+AES-GCM"
kiosk-request-hkdf-info      = "smart-health-checkin-kiosk-request-v1"
kiosk-response-hkdf-info     = "smart-health-checkin-kiosk-response-v1"
kiosk-content-encryption     = "A256GCM"
kiosk-submission-payload     = "smart-health-checkin-response"
kiosk-active-provider        = "instantdb"
kiosk-blob-content-type      = "application/octet-stream"
```

The active implementation evidence for these constants is in `rp-web/src/kiosk/protocol.ts` and `rp-web/src/kiosk/kiosk-provider.ts`; the slim provider row and permissions evidence is in `rp-web/src/kiosk/instant-mailbox.ts`, `rp-web/src/instant/schema.ts`, `rp-web/instant.perms.ts`, and `docs/plans/kiosk-transport-row-slim.md`.

## C.K.2 Deterministic JSON used by kiosk wrapper bytes

For the kiosk request compact JWS protected header and payload, the active profile signs base64url-encoded UTF-8 JSON generated by a deterministic rule: recursively sort object member names lexicographically, omit members whose value is `undefined`, preserve array order, and serialize with JSON stringification. The active implementation exposes this as `canonicalJson` in `rp-web/src/kiosk/protocol.ts`.

The same deterministic JSON rule is used by the active response-submission encryptor for `SubmissionPlaintext` byte counting and encryption input. This rule is scoped to the kiosk wrapper artifacts in this appendix. It does not define canonical JSON for the transport-neutral SMART request or SMART response outside the kiosk JWS or submission plaintext bytes.

A deterministic fixture vector for a kiosk JWS or response submission SHOULD publish the exact protected-header JSON bytes, payload JSON bytes, signing input, plaintext bytes, and corresponding parsed JSON values. The current repository has implementation tests for the active behavior, but it does not contain a checked-in deterministic kiosk byte vector with fixed keys, IVs, ciphertext, and expected signatures.

## C.K.3 Compact kiosk request JWS

The compact kiosk request JWS is the plaintext encrypted inside `EncryptedKioskRequest`. Its protected header has this constrained shape:

```cddl
kiosk-request-jws-header = {
  "alg" => "ES256",
  "kid" => non-empty-tstr,
  "typ" => "smart-health-checkin+kiosk-request+jws",
  * tstr => any
}
```

A Kiosk creator SHALL use compact JWS serialization with exactly three non-empty base64url segments. The signing input is:

```text
b64u(utf8(deterministic-json(kiosk-request-jws-header))) || "." ||
b64u(utf8(deterministic-json(KioskRequestPayload)))
```

A Phone presenter SHALL verify the ES256 signature over the exact compact-JWS signing input before using any payload field. A fixture that mutates JSON member order without changing the base64url segments is not an equivalent byte vector; the signature input is the original compact serialization.

## C.K.4 `KioskRequestPayload`

`KioskRequestPayload` is the signed kiosk request body. It embeds the §5 SMART request directly as `smartRequest`; it does not contain a request profile wrapper, preset, IPS shortcut, broad “all of the above” shortcut, or inline §8 request material.

```cddl
KioskRequestPayload = {
  "v" => 1,
  "iss" => non-empty-tstr,
  "aud" => non-empty-tstr,
  "requestId" => non-empty-tstr,
  "createdAt" => NumericDateMs,
  "expiresAt" => NumericDateMs,
  "submitTo" => SubmitTo,
  "smartRequest" => SmartHealthCheckinRequest,
  "encryptRequestTo" => EncryptRequestTo,
  "encryptResponseTo" => EncryptResponseTo,
  "constraints" => KioskConstraints,
  "minter" => KioskMinter,
  * tstr => any
}

SubmitTo = {
  "backend" => "instantdb",
  "appId" => non-empty-tstr,
  * tstr => any
}

EncryptRequestTo = {
  "alg" => "ECDH-P256+HKDF-SHA256+AES-GCM",
  "keyId" => non-empty-tstr,
  * tstr => any
}

EncryptResponseTo = {
  "alg" => "ECDH-P256+HKDF-SHA256+AES-GCM",
  "desktopPublicKeyJwk" => P256JWK,
  * tstr => any
}

KioskConstraints = {
  "maxPlaintextBytes" => uint,
  * tstr => any
}

KioskMinter = {
  "keyId" => non-empty-tstr,
  * tstr => any
}
```

A Kiosk creator SHALL set `requestId` to the wrapper identifier used by the Pointer URL, provider lookup, encrypted request envelope, response-submission HKDF salt/AAD, submission rows, and completion correlation. `requestId` is distinct from `smartRequest.id`; the inner `SmartHealthCheckinResponse.requestId` later binds to `smartRequest.id` under §6.

A Kiosk creator SHALL set `smartRequest` to a §5 `SmartHealthCheckinRequest` object before signing. The active request creation code signs `submitTo.backend`, `submitTo.appId`, `encryptResponseTo.desktopPublicKeyJwk`, `constraints.maxPlaintextBytes`, and `minter.keyId` along with the SMART request. A Phone presenter SHALL preserve these signed values for §§9.7-9.12 processing.

`createdAt`, `expiresAt`, and `submittedAt` in this kiosk profile are numeric milliseconds since the Unix epoch. Deployments still define accepted clock skew, maximum lifetime, and completion grace windows.

## C.K.5 `EncryptedKioskRequest`

`EncryptedKioskRequest` is the opaque request envelope stored or served by the Submission service. Its plaintext is the compact kiosk request JWS encoded as UTF-8 text.

```cddl
EncryptedKioskRequest = {
  "v" => 1,
  "alg" => "ECDH-P256+HKDF-SHA256+AES-GCM",
  "enc" => "A256GCM",
  "contentType" => "application/smart-health-checkin-kiosk-request+jws+aesgcm",
  "requestId" => non-empty-tstr,
  "createdAt" => NumericDateMs,
  "expiresAt" => NumericDateMs,
  "creatorKeyId" => non-empty-tstr,
  "recipientKeyId" => non-empty-tstr,
  "iv" => b64u-96-bit-iv,
  "ciphertext" => b64u-aes-gcm-ciphertext-and-tag,
  "ephemeralPublicKeyJwk" => P256JWK,
  * tstr => any
}
```

For request-envelope encryption:

```text
ECDH public recipient = request-opening P-256 key identified by recipientKeyId
HKDF hash             = SHA-256
HKDF salt             = utf8(requestId)
HKDF info             = utf8("smart-health-checkin-kiosk-request-v1")
AES-GCM key length    = 256 bits
AES-GCM IV            = base64url-decode(iv), 96 bits
AES-GCM AAD           = utf8(requestId)
plaintext             = utf8(compact kiosk request JWS)
ciphertext field      = b64u(AES-GCM ciphertext || tag)
```

A Kiosk creator SHALL mirror the signed payload `requestId`, `createdAt`, and `expiresAt` into the envelope, SHALL set `creatorKeyId` from the JWS protected header `kid`, and SHALL set `recipientKeyId` from `KioskRequestPayload.encryptRequestTo.keyId`. A Phone presenter SHALL bind at least the Pointer URL `r`, provider row `requestId` when present, envelope `requestId`, and verified payload `requestId` by exact string equality before same-device re-entry. Fixture profiles can add byte-exact checks for mirrored timestamps and key ids.

## C.K.6 Provider request row abstraction

The provider request row is a relay abstraction, not a clinical object and not an InstantDB schema requirement. The active slim request row is equivalent to:

```cddl
KioskRequestRow = {
  "requestId" => non-empty-tstr,
  "encryptedRequest" => EncryptedKioskRequest,
  * tstr => any
}
```

The untrusted provider can index, route, authorize, rate-limit, or clean up by `requestId` and operational metadata. It SHALL NOT require plaintext `KioskRequestPayload`, plaintext `smartRequest`, request-opening private key material, or creator signing private key material to route the request. Active demo private keys in `rp-web/src/kiosk/demo-keys.ts` are intentionally public prototype material and are not production key custody.

## C.K.7 `SubmissionPlaintext`

`SubmissionPlaintext` is the UTF-8 JSON object encrypted by the Phone presenter for the Completion display after §9.7 and phone-local §8 processing.

```cddl
SubmissionPlaintext = {
  "requestId" => non-empty-tstr, ; kiosk wrapper requestId
  "submittedAt" => NumericDateMs,
  "payload" => SubmissionPayload,
  * tstr => any
}

SubmissionPayload = SmartHealthCheckinResponsePayload / ExtensionSubmissionPayload

SmartHealthCheckinResponsePayload = {
  "kind" => "smart-health-checkin-response",
  "smartResponse" => SmartHealthCheckinResponse,
  * tstr => any
}
```

For the active successful payload, a Phone presenter SHALL set `payload.kind` to `smart-health-checkin-response` and `payload.smartResponse` to a §6 `SmartHealthCheckinResponse`. The outer `SubmissionPlaintext.requestId` is the kiosk wrapper request id. The inner `payload.smartResponse.requestId` is the clinical SMART request id, `KioskRequestPayload.smartRequest.id`.

A Phone presenter SHALL enforce the signed `KioskRequestPayload.constraints.maxPlaintextBytes` over the exact UTF-8 bytes it will encrypt. The active prototype uses 25 MiB for `maxPlaintextBytes` and rejects encrypted blobs larger than that plus 1024 bytes, but those numbers are prototype/deployment limits unless adopted by a conformance profile.

The active successful submission payload does not include plaintext `DeviceResponse`, `dcapiResponse`, §8 HPKE bytes, raw §8 `deviceRequest`, raw §8 `encryptionInfo`, private keys, provider credentials, or unrelated diagnostics.

## C.K.8 Response-submission encrypted payload and row metadata

The response-submission ciphertext is distinct from `EncryptedKioskRequest` and distinct from §8 HPKE. It encrypts the `SubmissionPlaintext` bytes to `KioskRequestPayload.encryptResponseTo.desktopPublicKeyJwk`.

```cddl
EncryptedSubmissionPayload = {
  "iv" => b64u-96-bit-iv,
  "ciphertext" => bytes, ; opaque AES-GCM ciphertext || tag, stored as a blob
  "phoneEphemeralPublicKeyJwk" => P256JWK,
  * tstr => any
}

KioskSubmissionRow = {
  "submissionId" => non-empty-tstr,
  "requestId" => non-empty-tstr,
  "storagePath" => non-empty-tstr,
  "storageFileId" => non-empty-tstr,
  "iv" => b64u-96-bit-iv,
  "phoneEphemeralPublicKeyJwk" => P256JWK,
  * tstr => any
}
```

For response-submission encryption:

```text
ECDH public recipient = signed encryptResponseTo.desktopPublicKeyJwk
HKDF hash             = SHA-256
HKDF salt             = utf8(KioskRequestPayload.requestId)
HKDF info             = utf8("smart-health-checkin-kiosk-response-v1")
AES-GCM key length    = 256 bits
AES-GCM IV            = base64url-decode(row.iv), 96 bits
AES-GCM AAD           = utf8(KioskRequestPayload.requestId)
plaintext             = utf8(deterministic-json(SubmissionPlaintext))
blob bytes            = AES-GCM ciphertext || tag
blob content type     = application/octet-stream
```

The active InstantDB row keeps `submissionId`, wrapper `requestId`, `storagePath`, `storageFileId`, `iv`, and `phoneEphemeralPublicKeyJwk`; ciphertext is stored as an opaque blob at `submissions/<requestId>/<submissionId>.bin`. The row does not currently require `payloadSha256`, content type, plaintext size, ciphertext size, or timestamp columns. Provider profiles MAY add operational diagnostics, but those fields SHALL NOT replace AES-GCM authentication, decrypted `requestId` validation, §6 validation, §7 trust interpretation, or §8 validation accounting.

# Appendix D kiosk fixture index and classification

Appendix D should only list kiosk material that exists or whose generation process is explicitly planned. Checked-in material is not a normative conformance vector merely because it exists. Kiosk fixture entries should identify byte-exact, structure-exact, semantic, or diagnostic-only expectations; PHI status; public demo key status; and whether keys/certificates are production, self-signed, test-only, or unknown.

## D.K.2 Existing material that is not current enough for normative kiosk examples

No checked-in fixture root currently appears to contain a deterministic kiosk request JWS round-trip vector, encrypted kiosk request envelope vector, pointer URL vector, phone resolution vector, response-submission ciphertext/blob vector, or wrong-AAD / wrong-request-id negative vector with fixed inputs and expected outputs.

The existing Chrome/Android captures should remain same-device diagnostic and historical material until a refreshed kiosk capture is produced. They were created for §8 request/response byte review and do not include the current T4.A/T4.B/T4.C wrapper artifacts: direct signed `smartRequest` kiosk JWS, `application/smart-health-checkin-kiosk-request+jws+aesgcm` envelope, pointer-only `#r=<requestId>`, slim provider request row, slim submission row, encrypted response blob, and desktop completion decryption/validation. A future kiosk example MAY reuse a refreshed same-device Chrome/Android capture as the phone-local §8 portion, but it should not silently promote older same-device captures into kiosk conformance vectors.

## D.K.3 Recommended future kiosk fixture vectors

A future kiosk fixture suite should include these vector classes once §9, §16.6, Appendix C, Appendix D, and conformance requirements are stable:

1. **Deterministic compact JWS signing input.** Publish protected header JSON bytes, payload JSON bytes, base64url segments, signing input, ES256 public JWK, test-only private JWK if needed, signature, and verification result. Include a negative vector for wrong `typ`, wrong `alg`, unknown `kid`, and mutated payload bytes.
2. **Encrypted request envelope.** Publish compact JWS plaintext bytes, request-opening public/private test JWKs, ephemeral public JWK, IV, HKDF salt `requestId`, info `smart-health-checkin-kiosk-request-v1`, AAD `requestId`, ciphertext+tag, and opened payload. Include negative vectors for wrong `requestId` AAD, wrong recipient key, malformed JWK, malformed IV, unsupported `contentType`, expired request, and envelope/payload id mismatch.
3. **Pointer URL.** Publish the exact Pointer URL using fragment `#r=<requestId>` and assert that it contains no plaintext SMART request, compact JWS, encrypted envelope, §8 `deviceRequest`, §8 `encryptionInfo`, SMART response, submission ciphertext, or secrets.
4. **Phone resolution and same-device re-entry.** Publish provider row, envelope, verified payload, extracted `smartRequest`, and the freshly constructed §8 same-device request artifacts generated on the phone. Include a negative vector for a legacy inline same-device descriptor being ignored or rejected.
5. **Response-submission encryption/decryption.** Publish `SubmissionPlaintext` JSON bytes, desktop P-256 public/private test JWKs, phone ephemeral public JWK, IV, HKDF salt/AAD wrapper `requestId`, info `smart-health-checkin-kiosk-response-v1`, ciphertext blob, slim submission row, and decrypted plaintext.
6. **Wrong request-id / AAD failures.** Include ciphertext swapping across two request ids, provider row `requestId` mismatch, storage path mismatch, decrypted `SubmissionPlaintext.requestId` mismatch, and response `smartResponse.requestId` mismatch against `smartRequest.id`.
7. **Expired request and freshness policy.** Include request envelopes and signed payloads at boundary times for not-yet-valid, expired, and acceptable clock-skew cases, with expected failure categories but without standardizing deployment-specific clock skew unless a profile does so.
8. **Oversized plaintext and blob.** Include vectors where deterministic `SubmissionPlaintext` bytes exceed signed `constraints.maxPlaintextBytes`, and where blob size exceeds an implementation/deployment limit. Do not make the prototype 25 MiB value universal unless adopted by a conformance profile.
9. **Malformed row/JWK/IV.** Include missing `encryptedRequest`, missing `storagePath`, malformed base64url IV, IV not 96 bits, unacceptable P-256 JWK coordinates, wrong JWK use, and missing `phoneEphemeralPublicKeyJwk`.
10. **Duplicate rows and replay.** Include multiple submissions for one wrapper `requestId`, replay of the same row/blob, and a valid later duplicate after one accepted submission. Expected results should distinguish cryptographic validity from workflow acceptance.
11. **No plaintext leakage.** Include machine-checkable assertions that request rows, submission rows, pointer URLs, storage paths, and encrypted blobs do not contain clinical display strings, profile URLs, raw FHIR JSON, SMART Health Cards, compact JWS plaintext, §8 `DeviceResponse`, `dcapiResponse`, private keys, or provider credentials.

## D.K.4 Prerequisites for a refreshed kiosk capture

A refreshed kiosk capture should be requested only after §8, §9, §16.6, Appendix C, Appendix D, and Appendix A expectations are stable. The stable prerequisites are:

- final SMART request and SMART response example JSON for the kiosk scenario;
- final test-only creator signing keys, request-opening keys, and desktop response-encryption keys, clearly marked public/non-production;
- deterministic JSON and byte-boundary rules for JWS and `SubmissionPlaintext`;
- fixed fixture-mode entropy inputs or recorded ephemeral keys/IVs for reproducibility;
- a stable pointer base URL and expected `#r=<requestId>` fragment;
- a stable provider row abstraction and storage-path convention;
- a stable same-device §8 fixture or capture for the phone-local re-entry portion; and
- expected pass/fail assertions for all negative vectors.

The outputs should include parsed and byte-level artifacts for the compact JWS, encrypted request envelope, provider request row, pointer URL, phone-local §8 request/response or reference to a same-device fixture, `SubmissionPlaintext`, encrypted response blob, submission row, desktop decryption result, validation report, and no-plaintext-leakage report.

# Organizer notes

## Strengths

- Aligns Appendix C kiosk shapes with accepted T4.A/T4.B/T4.C field names, algorithms, content type, pointer-only URL, direct `smartRequest`, and response-submission binding.
- Keeps request-envelope crypto, response-submission crypto, and §8 HPKE separate.
- Conservatively classifies existing repository material and avoids inventing byte-level vectors that are not checked in.
- Clearly marks active demo keys and active code/tests as prototype or diagnostic evidence rather than production trust anchors or normative fixtures.

## Caveats

- The pseudo-CDDL deliberately does not attempt complete JOSE/JWK/JSON Schema/InstantDB schema exactness.
- Active implementation validates some properties procedurally rather than through a complete schema; fixture profiles will need to decide which mirrored metadata checks become byte-exact requirements.
- The current desktop UI path opens and displays decrypted submissions but does not itself prove a standalone desktop-side §8 validation evidence story; T4.C leaves that to deployment trust boundaries.

## Open issues

- Decide in §13 or conformance profiles whether algorithm labels, JWS `typ`, payload `kind`, provider backend identifiers, TTLs, entropy sizes, clock skew, duplicate-member handling, and canonical JSON become registered or fixture-profile requirements.
- Decide whether a future provider profile adds optional ciphertext digest or row integrity hints; active code does not require them.
- Produce refreshed deterministic kiosk vectors before Appendix D or §16.6 treats kiosk examples as conformance candidates.

## Downstream dependencies

- T5.A/T5.F should extract conformance checklist rows only for requirements already stated in §9 or this appendix.
- T5.B/T5.C should cover QR substitution, pointer guessing, metadata leakage, demo key custody, logging, retention, duplicate submissions, and stale pointers.
- T6.B/T6.C should align worked kiosk examples and final fixture index entries with any refreshed kiosk capture.
